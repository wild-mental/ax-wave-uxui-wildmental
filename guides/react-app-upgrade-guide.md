# 최종 프로토타입을 React 앱 프로토타입으로 고도화하기 — 수업 뒤에

교재: Part 4를 마친 뒤 (4.7절 배포 · 4.8절 발표 다음) · 쓰는 곳: 새 작업 폴더 `axyourbody-app` · 출발 파일: Day 4에 만든 `prototype-final.html` · 함께 보는 가이드: 「[프로토타입 결과물을 goal 프롬프트로 일괄 완성도 높이기](goal-polish-guide.md)」

## 이 가이드에서 볼 것

수업에서 만든 프로토타입은 설치 없이 더블클릭으로 여는 HTML 한 파일입니다. 이 가이드는 수업이 끝난 뒤, 그 결과물을 **실제로 데이터를 저장하고 불러오는 앱 형태의 프로토타입**으로 키우는 순서를 안내합니다. 수업 중에 하지 않아도 되는 자료입니다.

세 단계로 나눕니다.

1. **PRD를 최종본으로 쓰기.** 4일 동안 워크시트에 쌓은 것을 한 문서로 모아, 무엇을 만들고 무엇을 만들지 않을지 먼저 못 박습니다.
2. **프론트엔드 원칙 문서 만들기.** 널리 쓰이는 화면·경험 원칙과 코드 품질 원칙을 내 서비스에 맞게 한 문서로 정리합니다.
3. **앱 만들기를 지시하기.** PRD, 원칙 문서, `prototype-final.html`을 기준으로 React · Vite · SQLite 앱을 만들게 하고, 원칙대로 됐는지 점검합니다.

순서가 중요합니다. AI로 개발하다 보면 **개발 범위를 제어하기 어려울 때**가 많습니다. 시키지 않은 기능이 붙고, 고치다 보면 처음 의도에서 조금씩 벗어납니다. 범위와 완료 기준을 적은 PRD가 먼저 있어야 AI가 그 안에서 일하고, 나도 "다 됐는지"를 판단할 수 있습니다. 원칙 문서를 먼저 자세히 넣는 이유는 「[프로토타입 결과물을 goal 프롬프트로 일괄 완성도 높이기](goal-polish-guide.md)」의 「먼저 읽을 것」과 같습니다.

| 낱말 | 풀이 |
|---|---|
| PRD | Product Requirements Document(우리말: 제품 요구사항 문서, 무엇을 왜 만들고 어디까지 만들지 적은 문서) |
| React | 화면을 부품(컴포넌트) 단위로 나눠 만드는 JavaScript 도구 |
| Vite | React 앱을 내 컴퓨터에서 바로 띄워 보고, 배포용 파일로 묶어 주는 실행 도구 |
| SQLite | 파일 하나에 데이터를 담는 가벼운 데이터베이스. 따로 서버 프로그램을 설치하지 않아도 됩니다 |

## 준비

- [ ] **Node.js**(LTS 버전)를 설치했다. React · Vite를 돌리는 데 필요합니다. [nodejs.org](https://nodejs.org)에서 받고, 설치한 뒤 Claude Code에 "node -v 와 npm -v 를 실행해서 버전을 보여 주세요."라고 보내 확인합니다.
- [ ] **새 작업 폴더**를 만들었다. 예) 바탕화면에 `axyourbody-app`. 수업 작업 폴더 `axyourbody-prototype`과 배포 전용 저장소는 그대로 둡니다.
- [ ] 새 폴더에 재료를 **복사**해 넣었다.

| 넣을 것 | 어디서 |
|---|---|
| `prototype-final.html` | 수업 작업 폴더 맨 위 (없으면 가장 최근 파일. 예: `prototype-improved.html`) |
| `context/` 폴더 통째로 | 수업 작업 폴더 (`service-structure.md` · `screen-flow.md` · `screen-layout.md` · `polish-principles.md` 등) |
| `design/my-own-DESIGN.md` | 수업 작업 폴더 |
| `data/` 폴더 통째로 | 수업 작업 폴더 (가상 프로필 CSV) |
| `docs/` 폴더 (새로 만들기) | PRD를 둘 곳 |

- [ ] 워크시트 저장소 `axyourbody-worksheet`를 브라우저에서 열어 두었다. PRD의 재료가 대부분 여기 있습니다.

**데이터는 가상 데이터만 씁니다.** 내 실제 신체·검진 수치, 증상, 대화 기록을 SQLite에 넣지 않습니다. 앱 폴더를 GitHub에 올릴 때도 데이터베이스 파일(`.db`, `.sqlite`)은 올리지 않습니다.

## 1단계 · PRD를 최종본으로 쓰기

### PRD 틀

아래 틀을 `docs/PRD.md`로 씁니다. 칸마다 아래 「칸별로 어디서 가져오나」를 보고 채웁니다.

```markdown
# PRD · AX YOUR BODY ({내 프로필 이름} 사용자용)

## 1. 개요·목표
- 문제 정의(Pain 지표 포함):
- 목표(Desired Outcome 수치화):
- 성공 지표(북극성 / 보조 KPI):

## 2. 사용자와 페르소나
- 핵심 페르소나 요약 및 여정 Pain·Needs 링크:

## 3. 사용자 스토리와 수용 기준(AC, Acceptance Criteria)
- Story: As a <persona>, I want <goal>, so that <outcome>.
- AC: Given / When / Then (수치 포함) × 최소 3개

## 4. 기능 요구사항(FR, Functional Requirement)
- MoSCoW 우선순위와 근거(대안 대비 가치)
  - MUST:
  - SHOULD:
  - COULD:
  - WON'T:

## 5. 비기능 요구사항(NFR, Non-Functional Requirement)
- 성능: p95 응답 ≤ ___ ms
- 신뢰성: 월 가용성 ≥ ___%, 오류율 ≤ ___%
- 보안/비용: ___
- 모니터링 항목: 로그·대시보드·알림 기준

## 6. 데이터·인터페이스 개요
- 핵심 엔터티, 주요 필드:
- 외부/내부 API 개요(입출력·제약):
```

### 칸별로 어디서 가져오나

**1. 개요·목표**

| 칸 | 가져올 곳 | 쓰는 법 |
|---|---|---|
| 문제 정의 (Pain 지표 포함) | 과업·불편 목록의 우선순위 "상" 과업 · 사용성 테스트 기록표 | 불편을 한 문장으로 쓰고, 얼마나 자주·얼마나 오래 겪는지 수를 붙입니다. 예) 빈도 "주 3회", 짝 테스트에서 걸린 시간 "2분 40초 · 실패" |
| 목표 (Desired Outcome 수치화) | 위 Pain 지표 | Pain 지표가 어떻게 바뀌면 성공인지 같은 단위로 씁니다. 예) "걸린 시간 2분 40초 → 1분 이내" |
| 성공 지표 (북극성 / 보조 KPI) | 화면마다 세웠던 지표 · 사용성 테스트 기록표의 성공 여부·걸린 시간 | 화면별로 흩어진 지표를 **서비스 핵심 목표 1~3개**로 정렬합니다. 그중 하나를 북극성 지표로, 나머지를 보조 KPI로 둡니다 |

- 북극성 지표(North Star Metric: 서비스가 사용자에게 주는 핵심 가치를 가장 잘 보여 주는 지표 하나)는 "사용자가 가장 중요한 과업을 끝냈다"를 셀 수 있는 행동으로 바꾼 것입니다. 예) 운동 관리 앱이라면 "불편한 곳을 남기고 다음 운동 강도를 고른 주간 횟수".
- KPI(Key Performance Indicator: 핵심 성과 지표)는 북극성 지표를 끌어올리는 앞단의 지표입니다. 화면 하나에 하나씩 지표를 두었다면, 그 지표가 어느 핵심 목표를 돕는지 줄을 그어 봅니다. 어느 목표에도 이어지지 않는 지표는 뺍니다.
- 수치는 근거가 있는 것만 씁니다. 근거가 없으면 앞에 "짐작:"을 붙입니다. 워크시트와 같은 규칙입니다.

**2. 사용자와 페르소나**

| 칸 | 가져올 곳 | 쓰는 법 |
|---|---|---|
| 핵심 페르소나 요약 | 페르소나 카드 | 한 줄 정체성 · 목표 우선순위 · 핵심 과업 · 피해야 할 가정을 세 줄 안으로 줄입니다 |
| 여정 Pain·Needs 링크 | Figma 이벤트 보드 · 과업·불편 목록 | 다시 쓰지 않고 링크를 겁니다. 워크시트 저장소의 해당 제목 주소, Figma 파일 주소를 붙입니다 |

**3. 사용자 스토리와 수용 기준 (AC)**

사용자 스토리(user story: 사용자 입장에서 원하는 것을 한 문장으로 쓴 요구)는 과업·불편 목록의 JTBD 문장을 옮겨 씁니다.

| 과업·불편 목록 | 사용자 스토리 |
|---|---|
| 「~할 때」 상황 | (As a) 페르소나 이름 + 상황 |
| 「~하고 싶다」 하려는 일 | I want 하려는 일 |
| 「그래서 ~」 | so that 결과 |

수용 기준(AC: 이 기능이 "됐다"고 판단하는 조건)은 스토리마다 **최소 3개**, Given(이런 상태에서) / When(이렇게 하면) / Then(이렇게 된다) 형식으로, **수를 넣어** 씁니다. 수가 없으면 됐는지 안 됐는지 가릴 수 없습니다.

```markdown
- Given 지난 7일 기록이 있는 사용자가 운동 상세 화면에 있을 때
  When "불편한 곳 남기기"를 누르고 부위와 아픈 정도를 고르면
  Then 버튼을 누른 뒤 3번 이하로 눌러 저장되고, 저장된 기록이 1초 안에 불편한 곳 목록 맨 위에 보인다
- Given 기록이 하나도 없는 사용자일 때
  When 동작별 기록 화면을 열면
  Then 빈 상태 안내와 "첫 기록 남기기" 버튼 1개가 보이고, 0이나 빈 차트는 보이지 않는다
- Given 저장 중 네트워크가 끊겼을 때
  When 저장을 누르면
  Then 입력한 값이 지워지지 않고, "저장 실패 · 다시 시도" 알림 띠가 보인다
```

예시는 「[화면 배치 먼저 정하고 테마 입히기](layout-first-theme-guide.md)」의 예시 운동 관리 앱입니다. 교재의 네 프로필 중 누구의 것도 아닙니다. 상태 화면 AC는 프로토타입의 상태 미리 보기(빈 상태 · 오류 · 로딩 · 이상치)에서 그대로 가져올 수 있습니다.

**4. 기능 요구사항 (FR)**

MoSCoW(MSCW: 꼭 · 되도록 · 여유가 있으면 · 이번에는 안 함의 네 단계로 나누는 우선순위 방법)로 나눕니다. **범위를 제어하는 칸**이라 가장 공들여 씁니다.

| 단계 | 뜻 | 무엇을 넣나 |
|---|---|---|
| MUST | 없으면 가장 중요한 과업을 끝낼 수 없다 | 3번 사용자 스토리의 AC가 걸린 기능. 처음 만들 때는 이것만 만듭니다 |
| SHOULD | 없어도 과업은 끝나지만 불편이 남는다 | 사용성 테스트의 "헤맴" · "거슬림" 이슈를 푸는 기능 |
| COULD | 있으면 좋다 | 프로토타입에 있었지만 핵심 과업과 거리가 먼 화면·기능 |
| WON'T | **이번에는 만들지 않는다** | 로그인·회원가입, 결제, 알림 보내기, 실제 기기 연동, 실제 AI 모델 호출 등 |

- 줄마다 **근거(대안 대비 가치)** 를 붙입니다. "이 기능 대신 무엇을 할 수도 있었는데, 왜 이것인가"를 한 줄로 씁니다. 예) "MUST · 불편한 곳 빠른 기록 — 세트 입력 안에 넣는 안보다 운동 없이도 남길 수 있어 과업 1을 바로 푼다(서비스 구조 설명서 8번)".
- **WON'T를 비워 두지 않습니다.** AI는 적히지 않은 기능을 "있으면 좋을 것"으로 채웁니다. 만들지 않을 것을 이름으로 적어야 범위가 지켜집니다.
- 서비스 구조 설명서 8번 「하지 말 것」은 FR 아래에 그대로 옮겨 둡니다.

**5. 비기능 요구사항 (NFR)**

비기능 요구사항은 "무엇을 하나"가 아니라 "얼마나 빠르고, 믿을 만하고, 안전한가"입니다. 내 컴퓨터에서 도는 프로토타입이므로 수치는 작게, 확인할 수 있는 것으로 정합니다.

| 칸 | 풀이 | 프로토타입에서 정하는 법 |
|---|---|---|
| 성능: p95 응답 ≤ ___ ms | p95(95번째 백분위수: 요청 100번 중 가장 느린 5번을 뺀 나머지가 모두 이 시간 안에 끝남) | 내 컴퓨터에서 목록 불러오기·저장하기의 목표 시간. 예) 300ms |
| 신뢰성: 월 가용성 ≥ ___%, 오류율 ≤ ___% | 가용성(한 달 중 서비스가 켜져 있는 시간의 비율), 오류율(요청 중 실패한 비율) | 공개 서비스가 아니면 가용성은 "해당 없음(내 컴퓨터에서만 실행)"으로 적어도 됩니다. 오류율은 AC를 다시 돌렸을 때 실패 0건처럼 셀 수 있게 씁니다 |
| 보안/비용 | 개인정보와 돈이 새는 곳 | "가상 데이터만 쓴다 · 데이터베이스 파일은 저장소에 올리지 않는다 · 유료 외부 API를 부르지 않는다(WON'T와 같음)" |
| 모니터링 항목: 로그·대시보드·알림 기준 | 무슨 일이 일어났는지 남기고 보는 방법 | 저장 실패·불러오기 실패를 터미널 로그에 남긴다 · 화면에 오류 알림 띠를 띄운다. 대시보드와 알림 보내기는 프로토타입에서는 WON'T로 두어도 됩니다 |

**6. 데이터·인터페이스 개요**

| 칸 | 가져올 곳 | 쓰는 법 |
|---|---|---|
| 핵심 엔터티, 주요 필드 | 대상 객체 카드 · 개념 ERD · 용어 대조표 | 대상 객체 하나가 엔터티(entity: 데이터베이스의 표 하나가 되는 것) 하나입니다. 핵심 속성이 필드, 관계(1:N 등)가 표끼리의 연결이 됩니다. 필드 이름은 용어 대조표의 **시스템 용어**로, 화면에는 **사용자 용어**로 씁니다 |
| 외부/내부 API 개요 (입출력·제약) | 화면 흐름 순서표 · FR의 MUST | API(Application Programming Interface: 화면과 데이터 사이에 정한 주고받기 약속). MUST 기능마다 "무엇을 보내면 무엇이 돌아오는지"를 한 줄로 씁니다. 예) "불편한 곳 저장: 부위·종류·아픈 정도(0~10)를 보내면 저장된 기록 하나가 돌아온다. 아픈 정도가 0~10 밖이면 거절" |

- `data` 폴더 CSV의 열 이름은 [데이터셋 열 이름 안내](../datasets/README.md)를 봅니다. CSV를 처음 데이터로 불러오는 것(가져오기)도 내부 API 한 줄로 적습니다.
- 외부 API는 프로토타입에서는 쓰지 않는 것을 기본으로 합니다. 쓰려면 FR의 MUST나 SHOULD에 먼저 올립니다.

### Claude Code로 PRD 초안 받기

틀을 혼자 다 채우기 어렵다면 초안을 받고, 빈칸은 내가 정합니다. 새 작업 폴더 `axyourbody-app`을 Code 탭에서 열고 보냅니다.

```text
@context/service-structure.md @context/screen-flow.md @context/screen-layout.md @design/my-own-DESIGN.md @prototype-final.html 을 먼저 모두 읽어 주세요.
아래에 붙이는 워크시트 내용과 PRD 틀로 docs/PRD.md 초안을 만들어 주세요.

1. 틀의 제목과 순서는 바꾸지 마세요.
2. 수치는 제가 붙인 워크시트와 data 폴더 CSV에 있는 것만 씁니다. 근거가 없는 수치는 앞에 "짐작:"을 붙이고, 어디서 가져와야 할지 괄호로 적어 주세요.
3. 사용자 스토리는 과업·불편 목록의 우선순위 "상" 과업마다 하나, AC는 스토리마다 3개 이상, Given / When / Then에 수를 넣어 씁니다.
4. FR은 MUST · SHOULD · COULD · WON'T로 나누고 줄마다 근거를 씁니다. WON'T에는 로그인·회원가입, 결제, 알림 보내기, 실제 기기 연동, 실제 AI 모델 호출을 기본으로 넣습니다.
5. 엔터티와 필드는 대상 객체 카드와 용어 대조표의 시스템 용어로 씁니다.
6. 제가 정해야 할 것은 채우지 말고 맨 아래 "정해야 할 것" 목록으로 남겨 주세요.

[PRD 틀]
{위 PRD 틀을 붙여 넣기}

[워크시트]
{과업·불편 목록 · 페르소나 카드 · 대상 객체 카드 · 용어 대조표 · 사용성 테스트 기록표를 워크시트 저장소에서 복사해 붙여 넣기}
```

**정해야 할 것 정하기.** 목록이 길면 grip-it으로 하나씩 정합니다. grip-it을 받는 법은 「[화면 배치 먼저 정하고 테마 입히기](layout-first-theme-guide.md)」 0단계와 같고, 이번에는 새 작업 폴더에 받습니다.

```text
/grip-it
참조 범위: @docs/PRD.md 와 그 맨 아래 "정해야 할 것"
관심 방향: 앱을 만들기 전에 PRD의 빈칸, 특히 성공 지표 · MUST/WON'T 경계 · NFR 수치를 확정한다.
완료 조건: "정해야 할 것"이 모두 정해지면 끝. 질문은 {8}개까지.
반영할 곳: 정한 것은 docs/PRD.md 에 고치고, 결정 기록부는 docs/grip-register.md 에 저장한다. 다른 파일은 고치지 않는다.
```

**PRD 점검.**

- [ ] 성공 지표가 1~3개로 정렬되어 있고, 북극성 지표가 하나다
- [ ] 스토리마다 AC가 3개 이상이고, AC마다 수가 들어 있다
- [ ] MUST 기능마다 그것을 확인하는 AC가 있다 (AC가 없는 MUST는 SHOULD로 내리거나 AC를 더합니다)
- [ ] WON'T가 비어 있지 않다
- [ ] "짐작:"이 남은 수치는 내가 받아들인 것이다
- [ ] 실제 개인 데이터가 한 줄도 없다

aztks 스킬이 있으면(「[프로토타입 결과물을 goal 프롬프트로 일괄 완성도 높이기](goal-polish-guide.md)」 0단계) "/aztks evaluate @docs/PRD.md 를 채점하고, 가장 큰 고칠 점 세 가지를 알려 주세요. 파일은 고치지 마세요."로 한 번 더 봅니다.

## 2단계 · 프론트엔드 원칙 문서 만들기

PRD는 "무엇을 만들지"를 정합니다. 이 단계는 "어떻게 보이고, 어떻게 말하고, 코드를 어떻게 짤지"를 정합니다. 적어 두지 않으면 AI가 기본값으로 채웁니다. 화면에서는 AI 슬롭이 되고, 코드에서는 고칠 때마다 다른 곳이 깨지는 코드가 됩니다.

널리 참고되는 두 공개 자료에서 이 프로토타입에 맞는 것만 골라 씁니다.

| 자료 | 무엇을 다루나 | 이 앱에서 쓰는 곳 |
|---|---|---|
| [토스 앱인토스 컨슈머 UX 가이드](https://developers-apps-in-toss.toss.im/design/consumer-ux-guide) | 사용자를 속이거나 가로막지 않는 화면(다크패턴 방지), 화면 문구(UX 라이팅), 그래픽, 탭바, 해상도 | 화면 · 문구 · 그래픽 · 모바일 폭 |
| [Frontend Fundamentals 코드 품질](https://frontend-fundamentals.com/code-quality/) | 변경하기 쉬운 코드의 네 기준: 가독성 · 예측 가능성 · 응집도 · 결합도 | React 부품(컴포넌트)과 폴더 구조 |

토스 가이드는 토스 안에서 돌아가는 미니앱의 출시 기준이라, 브랜드 로고 · SDK 설정 · 토스 제공 그래픽 리소스처럼 토스에만 해당하는 것은 뺍니다. 토스의 아이콘 · 이미지 같은 그래픽 자산은 토스 제휴 서비스 밖에서 쓸 수 없으므로 가져오지 않고, **원칙만** 씁니다.

### 화면 · 경험 원칙 (토스 컨슈머 UX 가이드에서)

**① 사용자를 가로막지 않기 (다크패턴 방지).** 다크패턴(dark pattern: 사용자가 원하지 않는 행동을 하도록 화면으로 속이거나 몰아가는 설계)을 만들지 않습니다.

| 원칙 | AX YOUR BODY에서는 |
|---|---|
| 들어오자마자 화면을 가리는 아래 시트(바텀시트)를 띄우지 않는다. 알림 허용을 묻는 시트도 같다 | 첫 화면을 열자마자 "기기 연결하기" · "알림 받기" 시트를 띄우지 않는다. 필요한 화면에서, 필요한 때 묻는다 |
| 뒤로 가기를 눌렀을 때 붙잡는 시트를 띄우지 않는다 | 기록을 쓰다 뒤로 가면 "작성 중인 내용이 있어요. 나갈까요?"처럼 사실만 알리고, 나가기를 막지 않는다 |
| 나갈 수 있는 선택지가 늘 있다 | 모든 시트 · 창에 닫기가 있다. 버튼 하나만 누르게 만든 화면이 없다 |
| 예상하지 못한 순간에 끼어들지 않는다 | 저장 버튼을 눌렀는데 다른 안내 창이 먼저 뜨지 않는다 |
| 버튼 문구만 보고 누르면 무엇이 되는지 안다. 버튼 위에 과장되거나 같은 말을 되풀이하는 설명을 두지 않는다 | "확인" · "시작하기" 대신 "불편한 곳 저장" · "다음 운동 강도 고르기". 버튼 위의 "지금 바로 건강을 지키세요!" 같은 문구는 뺀다 |

**② 화면 문구 (UX 라이팅).**

| 원칙 | 예 |
|---|---|
| 모든 문구를 해요체로 | "저장되었습니다" → "저장했어요" |
| 능동형으로. '되어요'는 '돼요'로 | "기록이 삭제됐어요" → "기록을 지웠어요" |
| 긍정형으로. 안 되는 것보다 하면 되는 것을 | "기록이 없어요" → "첫 기록을 남기면 여기서 볼 수 있어요" |
| 과한 높임말(~시겠어요?, ~께)을 쓰지 않기 | "저장하시겠어요?" → "저장할까요?" |
| '명사 + 명사'를 동사로 풀기 | "기록 저장 완료" → "기록을 저장했어요" |
| 창(다이얼로그)의 왼쪽 버튼은 "닫기". "취소"는 하던 일이 취소되는 것으로 오해할 수 있어 쓰지 않기 | [취소 · 지우기] → [닫기 · 지우기] |

예외도 있습니다. 민감한 상황에서 안심시킬 때, 정책상 쓸 수 없을 때는 수동형 · 부정형을 써도 되고, 쓸 수 없는 이유를 함께 알립니다. 건강 앱에서는 이런 때가 많습니다. 예) "이 기록만으로는 부상인지 판단할 수 없어요. 통증이 계속되면 전문가와 상의해 주세요."

**바꾸지 않는 것.** 서비스 구조 설명서의 "화면에 쓸 말"(화면 이름 · 메뉴 · 버튼에 쓰는 낱말)과 용어 대조표의 사용자 용어는 그대로 둡니다. 문장의 **말투만** 위 원칙으로 맞춥니다. `my-own-DESIGN.md`에 말투 규칙이 이미 있으면 그 규칙이 먼저입니다.

**③ 그래픽과 아이콘.**

- 장식이 아니라 화면의 뜻을 돕는 그래픽만 씁니다. 한 화면에 핵심 그래픽은 하나, 나머지는 작은 아이콘으로 대신합니다.
- 그래픽이 핵심 정보를 아래로 밀어내 스크롤을 늘리지 않게 둡니다.
- 의미 없는 묘사, 반짝이 효과(파티클), 과한 그라데이션을 쓰지 않습니다.
- 상황과 맞는 그래픽만 씁니다. 오류가 아닌데 느낌표 아이콘, 기다릴 필요가 없는데 로딩 애니메이션을 쓰지 않습니다.
- 슬픈 얼굴처럼 불쾌하거나 호소하는 감정 표현을 쓰지 않습니다. 예) 기록을 며칠 안 남긴 사용자에게 우는 캐릭터를 보이지 않습니다.
- 아이콘은 화면에서 24~40px 크기로, 아이콘이나 이모지를 여러 개 나란히 붙이지 않고 한 번에 하나만 씁니다.
- 라이트 · 다크 모드 모두에서 보이도록 너무 밝거나 어둡지 않은 중간 밝기의 색을 씁니다.

이 원칙은 「[프로토타입 결과물을 goal 프롬프트로 일괄 완성도 높이기](goal-polish-guide.md)」의 AI 슬롭 점검 목록 ①색과 장식 · ③글꼴과 아이콘과 겹칩니다. 수업 작업 폴더에서 `context/ai-slop-checklist.md`를 복사해 왔다면 함께 씁니다.

**④ 탭바와 모바일 폭.**

- 아래쪽 탭(탭바)은 2~5개입니다. 서비스 구조 설명서 6번의 메뉴 수가 이 안에 드는지 봅니다.
- 세로 화면은 논리 해상도(화면 배치를 계산하는 기준 크기) 하나를 정해 그 기준으로 맞춥니다. 토스 가이드의 권장 범위는 세로형 약 360×640 ~ 420×740입니다. 기기마다 다른 배치를 따로 만들지 않습니다.
- 모든 기기에서 시험하지 않아도 됩니다. 대표 크기 3~5개면 충분합니다. 브라우저 개발자 도구의 기기 모드(`Cmd+Shift+M` / `Ctrl+Shift+M`)에서 화면 비율이 다른 기기 2~3개, 화면 위쪽 노치(Safe Area: 노치·카메라 구멍을 피한 안전 영역)가 큰 기기 1개, 작은 화면 기기 1개를 골라 봅니다.

### 코드 원칙 (Frontend Fundamentals에서)

Frontend Fundamentals는 좋은 프론트엔드 코드를 **변경하기 쉬운 코드**로 봅니다. 프로토타입은 계속 고치는 것이 일이라, 고칠 때 다른 곳이 깨지지 않는 코드가 중요합니다. 코드를 직접 짜지 않더라도 이 네 기준으로 AI에게 지시하고, 질문으로 확인할 수 있습니다.

| 기준 | 뜻 | 사이트의 전략 | 이 앱에서는 |
|---|---|---|---|
| 가독성 | 읽기 쉬운가. 한 번에 생각할 맥락이 적고 위에서 아래로 읽히는가 | 같이 실행되지 않는 코드 분리하기 · 구현 상세 추상화하기 · 로직 종류에 따라 합쳐진 함수 쪼개기 · 복잡한 조건에 이름 붙이기 · 매직 넘버에 이름 붙이기 · 시점 이동 줄이기 · 삼항 연산자 단순하게 하기 · 왼쪽에서 오른쪽으로 읽히게 하기 | 빈 상태 · 오류 · 정상 화면을 한 부품 안의 조건문으로 뒤섞지 않고 상태별로 나눈다. "아픈 정도 7 이상이면 경고"의 7처럼 뜻이 있는 숫자(매직 넘버)에는 이름을 붙인다 |
| 예측 가능성 | 이름 · 받는 값 · 돌려주는 값만 보고 무엇을 하는지 알 수 있는가 | 이름 겹치지 않게 관리하기 · 같은 종류의 함수는 반환 타입 통일하기 · 숨은 로직 드러내기 | 데이터를 불러오는 함수들은 같은 모양으로 결과를 돌려준다. "저장" 함수 안에 몰래 화면 이동 · 기록 남기기를 숨기지 않는다 |
| 응집도 | 함께 고쳐야 하는 코드가 늘 함께 고쳐지는가 | 함께 수정되는 파일을 같은 디렉토리에 두기 · 매직 넘버 없애기 · 폼의 응집도 생각하기 | 폴더를 `components` · `hooks`처럼 종류별로만 나누지 않고, PRD 6번 엔터티(대상 객체)별로 묶는다. 예) 불편한 곳에 관한 화면 · 데이터 · 저장 코드를 한 폴더에 |
| 결합도 | 한 곳을 고치면 영향이 얼마나 퍼지는가 | 책임을 하나씩 관리하기 · 중복 코드 허용하기 · Props Drilling 지우기 | 한 부품이나 함수가 여러 일을 맡지 않는다. 화면 깊숙이 값을 줄줄이 넘기는 대신 부품을 조합(children)하는 방법을 먼저 쓰고, 그래도 안 될 때만 Context를 쓴다 |

사이트는 네 기준을 **한꺼번에 다 지키기는 어렵다**고 말합니다. 공통 코드로 묶으면 응집도는 오르지만 읽기 어려워지고, 중복을 허용하면 결합도는 내려가지만 한쪽만 고치는 실수가 생길 수 있습니다. 같이 고치지 않으면 오류가 나는 곳(예: 아픈 정도의 범위 0~10을 화면과 저장 쪽이 함께 써야 할 때)은 묶고, 그런 위험이 적으면 읽기 쉬운 쪽을 고르라고 합니다. 이 판단 순서도 원칙 문서에 적어 둡니다.

### 원칙 문서 만들기

새 작업 폴더에서 보냅니다. 원칙을 다시 지어내지 않도록, 이 가이드에 정리한 내용을 붙여 넣어 씁니다.

```text
@docs/PRD.md @context/service-structure.md @design/my-own-DESIGN.md 를 먼저 모두 읽어 주세요.
아래 [화면 · 경험 원칙]과 [코드 원칙]을 이 서비스에 맞게 docs/frontend-principles.md 로 정리해 주세요.

1. 원칙마다 "이 앱에서는"을 한 줄씩 붙입니다. 화면 이름 · 버튼 문구는 service-structure.md 의 "화면에 쓸 말"을 씁니다.
2. my-own-DESIGN.md 나 service-structure.md 8번 "하지 말 것"과 부딪히는 원칙은 그 문서 쪽을 따르고, 부딪힌 줄을 맨 아래 "부딪힌 것"에 적어 주세요.
3. 화면 문구 원칙은 문장의 말투에만 적용합니다. "화면에 쓸 말"의 낱말은 바꾸지 않습니다.
4. 코드 원칙에는 폴더를 PRD 6번 엔터티별로 나눈 예시 폴더 구조를 넣어 주세요.
5. 맨 끝에 원칙끼리 부딪힐 때의 순서를 적습니다: PRD의 AC > "하지 말 것" > my-own-DESIGN.md > 화면 · 경험 원칙 > 코드 원칙. 코드 원칙끼리는 "같이 안 고치면 오류가 나는가"로 응집도와 가독성 중에서 고릅니다.
6. 다 만든 뒤 원칙마다 확인하는 방법(화면에서 눌러 볼 것, 또는 제가 Claude Code에 물어볼 질문)을 표로 보여 주세요.

[화면 · 경험 원칙]
{이 가이드의 「화면 · 경험 원칙」 ①~④를 복사해 붙여 넣기}

[코드 원칙]
{이 가이드의 「코드 원칙」 표와 그 아래 문단을 복사해 붙여 넣기}
```

**확인.**

- [ ] 원칙마다 "이 앱에서는" 줄이 있고, 화면 이름이 "화면에 쓸 말"과 같다
- [ ] 화면 문구 원칙이 "화면에 쓸 말"의 낱말을 바꾸라고 하지 않는다
- [ ] 예시 폴더 구조가 엔터티별로 나뉘어 있다
- [ ] 부딪힐 때의 순서가 적혀 있다

화면 · 경험 원칙은 HTML 프로토타입에도 그대로 쓸 수 있습니다. 수업 작업 폴더의 `prototype-final.html`에 먼저 적용해 보고 싶다면, 원칙 문서를 「[프로토타입 결과물을 goal 프롬프트로 일괄 완성도 높이기](goal-polish-guide.md)」 1단계의 `polish-principles.md` "없앨 것 · 채울 것"에 더해 같은 흐름으로 맡깁니다.

## 3단계 · React 앱 만들기 지시하기

### 기본 지시

핵심은 이 한 문장입니다.

```text
지금부터 화면 시안 및 프로토타입 결과물로 만들어진 HTML file을 기준으로 본격적인 Front-end 앱을 제작하고 싶어. React 프레임워크를 사용하고 실행 환경으로는 Vite를 사용해줘. 데이터베이스는 파일 기반의 경량 데이터 관리가 가능한 sqlite를 사용해줘
```

이 문장만 보내면 AI가 범위·구조·데이터를 기본값으로 채웁니다. 아래처럼 PRD와 지킬 것을 붙여, **계획부터** 받습니다.

### ① 계획 받기 (Plan 모드)

입력창 아래 **모드 선택**에서 **Plan**을 고르고 보냅니다.

```text
계획만 세웁니다. 파일은 만들거나 고치지 마세요.
@docs/PRD.md @docs/frontend-principles.md @prototype-final.html @context/service-structure.md @context/screen-flow.md @design/my-own-DESIGN.md 를 먼저 모두 읽어 주세요.

지금부터 화면 시안 및 프로토타입 결과물로 만들어진 HTML file을 기준으로 본격적인 Front-end 앱을 제작하고 싶어. React 프레임워크를 사용하고 실행 환경으로는 Vite를 사용해줘. 데이터베이스는 파일 기반의 경량 데이터 관리가 가능한 sqlite를 사용해줘.

[범위]
- PRD 4번 FR의 MUST만 만듭니다. SHOULD · COULD는 MUST가 모두 끝나고 제가 말하면 만듭니다. WON'T는 만들지 않습니다.
- 화면 목록 · 흐름 순서 · 화면에 쓸 말은 prototype-final.html 과 screen-flow.md 그대로 둡니다.
- 색 · 글꼴 · 간격은 my-own-DESIGN.md 를 따릅니다.
- 화면 · 문구 · 그래픽과 폴더 구조 · 부품 나누기는 frontend-principles.md 를 따릅니다. 부딪히면 그 문서 맨 끝의 순서로 정합니다.

[데이터]
- SQLite 데이터베이스 파일은 작업 폴더 안에 하나만 둡니다. 표와 열은 PRD 6번의 엔터티와 필드 이름을 씁니다.
- 처음 데이터는 data 폴더의 CSV에서 가져옵니다. 없는 값을 지어내지 마세요.
- 브라우저 화면이 SQLite 파일을 어떻게 읽고 쓰는지(작은 서버를 둘지, 다른 방법을 쓸지) 방법과 이유를 적어 주세요.

[계획에 넣을 것]
1. 폴더 구조와 파일 목록 (frontend-principles.md 의 엔터티별 폴더 구조를 따라)
2. 설치할 패키지 목록과 각각의 이유 (꼭 필요한 것만)
3. 데이터베이스 표 · 열 · 표끼리의 관계
4. 화면마다 만들 React 부품(컴포넌트) 목록과 prototype-final.html 의 어느 영역에서 오는지
5. MUST 기능마다 그것을 확인하는 PRD 3번의 AC
6. 만드는 순서 (한 번에 하나씩 확인할 수 있게 작은 단위로)
7. 내 컴퓨터에서 실행하는 명령과, 열어 볼 주소
마지막에 제가 정해야 할 것을 목록으로 남겨 주세요.
```

**계획 확인.**

- [ ] 만들 기능이 PRD의 MUST뿐이다 (로그인, 알림처럼 WON'T가 끼어 있으면 빼 달라고 합니다)
- [ ] 데이터베이스 표 이름 · 열 이름이 PRD 6번과 같다
- [ ] 설치 패키지가 지나치게 많지 않고, 줄마다 이유가 있다
- [ ] 화면 이름이 `screen-flow.md` 화면 목록과 같고, 새 화면이 없다
- [ ] 폴더가 `components` · `hooks`처럼 종류별로만 나뉘지 않고 엔터티별로 묶여 있다
- [ ] 브라우저와 SQLite를 잇는 방법이 적혀 있다. SQLite는 파일이라 브라우저가 바로 열 수 없어서, 보통 작은 서버(Node.js)가 그 파일을 읽고 쓰고 화면은 그 서버에 요청합니다

계획 끝의 승인 버튼은 누르지 않습니다. 모드를 **Manual**이나 **Accept edits**로 바꾼 뒤 ②로 갑니다.

### ② 작은 단위로 만들기

같은 대화에서 보냅니다.

```text
방금 계획의 만드는 순서대로, 첫 단위만 만들어 주세요.
만든 뒤 실행 명령과 열어 볼 주소, 이 단위에서 확인할 AC를 알려 주세요. 다음 단위는 제가 확인한 뒤 말하면 시작해 주세요.
```

- 설치(`npm install` 등)와 실행(`npm run dev` 등) 명령 허락을 물으면, **새 작업 폴더 안**에서 계획에 적힌 패키지를 설치하는 것일 때만 허락합니다. 작업 폴더 밖이나 컴퓨터 전체에 설치하는 명령(`-g`, `sudo`)은 거절합니다.
- 실행되면 알려 준 주소(보통 `http://localhost:5173`)를 브라우저로 엽니다. `prototype-final.html`과 나란히 열고, 같은 화면이 같은 순서·같은 문구로 보이는지 봅니다.
- 단위마다 해당 AC를 직접 해 봅니다. 수가 들어 있으므로 "됐다 · 안 됐다"를 가릴 수 있습니다. 안 되면 "AC '{AC 한 줄}'이 안 됩니다. {무엇이 어떻게} 됩니다. 이것만 고쳐 주세요."라고 한 가지씩 고칩니다.
- 화면을 새로 고쳐도, 실행을 껐다 켜도 저장한 기록이 남아 있으면 SQLite 저장이 된 것입니다.

MUST가 모두 끝나고 AC를 하나씩 통과하면, 남은 일을 `/goal`로 한꺼번에 맡겨도 됩니다. 이때 끝나는 조건을 "PRD 3번의 AC를 모두 확인한 표가 대화에 나온다", 범위를 "MUST만 · WON'T 금지"로 씁니다. 방법은 「[프로토타입 결과물을 goal 프롬프트로 일괄 완성도 높이기](goal-polish-guide.md)」 2~3단계와 같습니다.

### ③ PRD와 맞추기

만들다가 정한 것이 바뀌면 PRD도 같이 고칩니다. 예) "방금 정한 '불편한 곳 저장은 운동 없이도 된다'를 PRD 3번 AC와 6번 API 개요에 반영해 주세요. 다른 줄은 바꾸지 마세요." PRD와 앱이 어긋나면, 다음에 지시할 때 AI가 어느 쪽을 따라야 할지 모릅니다.

### ④ 원칙대로 됐는지 점검하기

MUST 단위를 두세 개 만들 때마다, 그리고 MUST를 다 만든 뒤 한 번 더 점검합니다. 점검은 고치기와 나눠서 받습니다.

```text
점검만 합니다. 파일은 고치지 마세요.
@docs/frontend-principles.md 의 원칙을 지금까지 만든 화면과 코드에 한 줄씩 대 보고 표로 보여 주세요.
열: 원칙 · 지켰음/어김 · 어긴 곳(화면 이름 또는 파일 이름과 줄) · 고칠 방향
코드 원칙은 어긴 곳마다 "이대로 두면 무엇을 고칠 때 어디가 같이 깨질 수 있는지"를 한 줄로 적어 주세요.
```

표를 보고 어긴 곳을 한 번에 한 가지씩 고칩니다. 예) "원칙 표의 '{원칙}' 줄만 고쳐 주세요. 고친 뒤 그 화면의 AC가 아직 통과하는지 알려 주세요. 다른 곳은 바꾸지 마세요." 고칠 곳이 많으면 「[프로토타입 결과물을 goal 프롬프트로 일괄 완성도 높이기](goal-polish-guide.md)」처럼 `/goal`로 한꺼번에 맡기되, 끝나는 조건에 "PRD의 AC가 모두 통과한다"를 꼭 넣습니다. 원칙을 지키려다 기능이 깨지면 안 되기 때문입니다.

직접 눌러 보며 볼 것도 있습니다.

- [ ] 첫 화면을 열자마자 가리는 시트나 창이 없다
- [ ] 모든 시트 · 창에 닫기가 있고, 뒤로 가기가 막히지 않는다
- [ ] 버튼 문구만 읽고 누르면 무엇이 되는지 안다
- [ ] 안내 · 오류 문구가 해요체이고, 창의 왼쪽 버튼이 "닫기"다
- [ ] 기기 모드에서 대표 크기 3~5개로 봤을 때 깨지는 화면이 없다

코드는 직접 읽지 않아도 질문으로 확인할 수 있습니다.

- "불편한 곳의 아픈 정도 범위를 0~10에서 1~10으로 바꾸려면 어느 파일을 고쳐야 하나요? 고치지 말고 목록만 알려 주세요." → 고칠 파일이 한 폴더 안에 한두 개면 응집도가 높은 것입니다. 여기저기 흩어져 있으면 그곳을 묶어 달라고 합니다.
- "저장 함수가 저장 말고 하는 일이 있나요?" → 있다면 숨은 로직입니다. 밖으로 드러내 달라고 합니다.

## 공개할 때

- 수업에서 쓴 GitHub Pages는 파일을 그대로 보여 주기만 하므로, SQLite를 읽고 쓰는 서버는 돌지 않습니다. 이 앱은 **내 컴퓨터에서 실행하는 프로토타입**으로 둡니다. 화면만 보여 주려면 수업의 배포 링크를 그대로 씁니다.
- 앱 폴더를 GitHub 저장소로 올린다면 데이터베이스 파일(`.db`, `.sqlite`)과 `node_modules` 폴더는 올리지 않게 `.gitignore`에 넣어 달라고 합니다. 올리기 전에 「[배포 전 점검과 정적 배포 가이드](pre-deploy-check-guide.md)」의 개인정보 점검을 한 번 더 합니다.

## 자주 하는 실수와 고친 예

| 실수 | 고친 예 |
|---|---|
| PRD 없이 기본 지시 한 문장만 보냈다. 예) 도서관 앱에서 로그인 · 관리자 화면 · 추천 기능까지 만들어져, 정작 대출 연장이 안 된다 | 만든 폴더는 이름 끝에 `-before-prd`를 붙여 두고, PRD의 MUST · WON'T를 먼저 쓴 뒤 ① 계획부터 다시 받는다 |
| AC에 수가 없다. 예) 배달앱 "주문 내역이 빠르게 보인다" | "주문 내역 화면을 열면 1초 안에 최근 주문 20건이 보인다"처럼 시간 · 개수를 넣는다 |
| WON'T를 비워 두어 기능이 계속 붙는다 | 붙은 기능의 이름을 WON'T에 적고, "PRD WON'T에 있는 {기능}을 빼 주세요. 다른 곳은 바꾸지 마세요."라고 보낸다 |
| 데이터베이스 열 이름이 화면 말과 섞였다. 예) 택배 앱의 표 열 이름이 "배송 조회" | 열 이름은 용어 대조표의 시스템 용어(`delivery_status` 등)로, 화면에는 사용자 용어로 쓰도록 PRD 6번을 고치고 다시 지시한다 |
| 원칙을 문서로 두지 않고 "깔끔하게 만들어 줘"만 보냈다. 예) 도서관 앱 첫 화면에 들어오자마자 "알림 받기" 시트가 뜨고, 닫기가 없다 | 2단계 원칙 문서를 만들고 "frontend-principles.md 의 가로막지 않기 원칙대로 첫 화면의 시트를 없애고, 알림은 대출 화면에서 묻게 해 주세요."라고 보낸다 |
| 화면 문구를 해요체로 바꾸다가 화면 이름까지 바뀌었다. 예) 배달앱 메뉴 "주문 내역"이 "주문한 것 보기"로 | "화면에 쓸 말"의 낱말은 되돌리고, 원칙 문서에 "말투 원칙은 문장에만"을 다시 적는다 |
| 폴더가 `components` · `hooks` · `utils`로만 나뉘어, 한 기능을 고치는데 파일 다섯 곳을 오간다 | "폴더를 PRD 6번 엔터티별로 다시 묶는 계획만 먼저 보여 주세요. 고치지 마세요."로 계획을 받고, AC가 그대로 통과하는지 확인하며 한 엔터티씩 옮긴다 |
| 실제 내 건강 기록을 넣어 시험했다 | 데이터베이스 파일을 지우고 `data` 폴더의 가상 CSV로 다시 가져오게 한다. 저장소에 올렸다면 저장소에서도 지운다 |

## 막혔을 때

- **`node`나 `npm`을 찾을 수 없다고 한다.** Node.js를 설치한 뒤 Claude 데스크톱 앱을 완전히 껐다 켭니다. Windows는 「[Windows 사용자 메모](../help/windows-notes.md)」도 봅니다.
- **SQLite 패키지 설치가 실패한다.** 오류 메시지 전체를 붙여 "이 오류의 원인을 한 줄로 설명하고, 설치가 필요 없는 다른 방법이 있으면 두 가지만 비교해 주세요. 아직 고치지 마세요."라고 보낸 뒤 고릅니다.
- **주소를 열었는데 빈 화면이다.** "실행 중인 터미널 로그와 브라우저 개발자 도구 콘솔에 나온 오류를 확인해서 원인을 알려 주세요."라고 보냅니다. 개발자 도구는 `Cmd+Option+I` / `F12`입니다.
- **화면이 `prototype-final.html`과 다르게 생겼다.** "{화면 이름}이 prototype-final.html 의 같은 화면과 다릅니다. {다른 곳}을 prototype-final.html 그대로 맞춰 주세요. 기능은 바꾸지 마세요."
- **사용량 한도가 다 되었다.** 다른 AI 코딩 도구로 이어서 할 수 있습니다. PRD와 계획이 파일에 있으므로 새 도구에서 "@docs/PRD.md 와 지금 폴더 구조를 읽고, 계획의 만드는 순서 중 남은 단위부터 이어 주세요."라고 보냅니다. 도구 차이는 「[다른 AI 코딩 도구로 할 때 (OpenAI Codex · Cursor)](../help/other-coding-tools.md)」를 봅니다.
