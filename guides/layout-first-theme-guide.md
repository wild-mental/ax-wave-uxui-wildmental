# 화면 배치 먼저 정하고 테마 입히기 — Day 3 실습 흐름

교재: 3.6절 Claude Code로 테마별 첫 프로토타입 만들기 (67~71쪽) · 쓰는 곳: 작업 폴더 `axyourbody-prototype` · 워크시트 문서의 「테마별로 만든 첫 프로토타입과 버전 기록」 · 함께 보는 가이드: 「[Claude Code 프로토타이핑 따라 하기](claude-code-prototyping-guide.md)」

## 이 가이드에서 볼 것

교재 3.6절은 첫 프로토타입을 만들 때 화면 배치와 디자인을 한 번에 정하게 합니다. 이 가이드는 그 사이를 둘로 나눕니다.

1. **배치 먼저.** 디자인을 입히기 전에, 화면마다 무엇을 **어떤 요소 유형**(카드, 목록, 표, 차트, 버튼…)으로 **어디에** 놓을지 정합니다. Claude Code에게 배치안을 2~3개 받고, grip-it 스킬로 하나씩 결정합니다.
2. **테마는 그다음.** 정한 배치 위에 DESIGN.md를 입힙니다. 이때 흐름의 순서와 과업에 꼭 필요한 동작만 지키면 **배치와 요소 유형은 테마가 바꿔도 된다**고 지시합니다. 그래서 테마마다 색만 바뀌는 것이 아니라 화면의 생김새와 쓰는 느낌까지 달라지고, 그 차이를 비교할 수 있습니다.

교재 3.6의 작업 폴더, 확인 목록 네 가지, 한 번에 한 가지씩 고치는 법, 상태 화면·신뢰 요소 지시문은 그대로 씁니다. 바뀌는 것은 **교재 70쪽 1단계와 3단계의 지시문**뿐입니다.

`{ }`로 감싼 부분은 내 내용으로 바꿔서 보냅니다. 1~3단계는 **한 대화 안에서** 이어서 합니다. 2단계의 grip-it이 1단계에서 받은 배치안을 읽기 때문입니다.

## 요소 유형 낱말

배치안을 읽고 결정할 때 쓰는 낱말입니다. 화면에 올라가는 것을 "무엇을 보여 주나(대상 객체·속성)"와 "어떤 모양으로 보여 주나(요소 유형)"로 나눠 생각합니다.

| 요소 유형 | 무엇인가 | 잘 맞는 때 |
|---|---|---|
| 카드 | 한 덩어리 정보를 테두리 상자 하나에 담은 것 | 하나를 눈에 띄게 보여 줄 때 (오늘 할 일 하나) |
| 목록 | 같은 모양의 줄을 위에서 아래로 늘어놓은 것 | 여러 개를 훑어볼 때 |
| 표 | 행과 열로 나눈 것 | 같은 항목을 여러 날·여러 개끼리 비교할 때 |
| 차트 | 숫자를 선·막대·달력 칸 같은 그림으로 바꾼 것 | 변화나 빈 날을 한눈에 볼 때 |
| 탭 | 같은 자리에서 내용을 바꿔 보는 머리 버튼 | 나란한 묶음 2~4개를 오갈 때 |
| 펼치기 | 제목만 보이다가 누르면 내용이 열리는 것 | 가끔만 보는 자세한 내용 |
| 버튼 | 눌러서 일을 일으키는 것 | 저장하기, 다음 화면으로 가기 |
| 칩 | 작게 눌러 고르는 꼬리표 모양 버튼 | 여러 보기 중에서 빠르게 고를 때 |
| 단계 선택 | 정해진 칸 중에서 하나를 고르는 줄이나 막대 | "무거움 ~ 가벼움"처럼 단계가 있는 값 |
| 입력 칸 | 글자나 숫자를 쳐 넣는 칸 | 정해진 보기가 없는 값 |
| 알림 띠 | 화면 위나 아래에 잠깐 또는 계속 뜨는 한 줄 안내 | 저장됨, 저장 실패 같은 결과 알리기 |
| 메뉴 | 화면 위쪽 탭, 왼쪽 메뉴, 모바일 아래쪽 탭 | 서비스 구조 설명서 6번의 메뉴 |

## 0단계 · grip-it 스킬 준비

grip-it은 정해야 할 것을 먼저 모두 펼쳐 보여 주고, 하나씩 **권장안과 이유를 붙여 선택지로** 물어보고, 정한 것을 바로 파일에 적어 두는 스킬입니다. 결정은 내가 하고, Claude Code는 선택지를 차려 놓습니다.

**지시.** Code 탭에서 `axyourbody-prototype` 폴더를 연 뒤 이렇게 보냅니다.

```text
https://github.com/wild-mental/grip-it-skill 저장소의 .claude/skills/grip-it/SKILL.md 파일을
이 작업 폴더의 .claude/skills/grip-it/SKILL.md 로 저장해 주세요.
내용을 읽고 다시 쓰지 말고, 파일째 그대로 내려받아 주세요. 이 파일 하나만 받고, 내 컴퓨터 전체 위치에는 저장하지 마세요.
저장한 뒤 파일의 줄 수와 첫 세 줄을 보여 주세요.
```

인터넷에서 파일을 받는 허락을 물으면, 받는 주소가 위의 `github.com/wild-mental/grip-it-skill`이나 `raw.githubusercontent.com/wild-mental/grip-it-skill`일 때만 허락합니다. 그 밖의 설치나 명령 실행은 거절합니다.

**이렇게 나오면 정상입니다.** 파일이 500줄이 넘고, 첫 줄이 `---`, 둘째 줄이 `name: grip-it`입니다. 입력창에 `/`를 치면 목록에 `grip-it`이 보입니다.

- 줄 수가 100줄도 안 된다 → 내용을 요약해서 저장한 것입니다. "방금 파일은 원문이 아닙니다. 지우고, 같은 주소의 파일을 내용을 바꾸지 않고 파일째 다시 내려받아 주세요." 안 보이면 새 대화를 열고 다시 봅니다. 숨은 폴더 보기와 `/` 목록 확인은 「[디자인 스킬 가져오기 가이드](design-skill-guide.md)」 4번과 같습니다.

## 1단계 · Plan 모드로 배치안 2~3개 받기

**모드 바꾸기.** 입력창 아래 **모드 선택**에서 **Plan**을 고릅니다(앱 버전에 따라 "Plan mode"로 보입니다). Plan 모드에서는 Claude Code가 파일을 만들거나 고치지 않고 계획만 돌려줍니다. 목록에 Plan이 없으면 Manual로 두고 그대로 보내면 됩니다. 지시문 첫 줄이 파일을 고치지 말라고 하기 때문입니다.

**지시.**

```text
계획만 세웁니다. 파일은 만들거나 고치지 마세요.
@context/service-structure.md @context/screen-flow.md 를 먼저 모두 읽어 주세요.
AX YOUR BODY의 {내 프로필 이름} 사용자를 위한 화면 배치안을 만듭니다.
색·글꼴·모양 같은 디자인은 아직 정하지 않습니다. 화면마다 무엇을, 어떤 요소 유형으로, 어디에 놓을지만 정합니다.

1. 서로 방향이 다른 배치안을 2~3개 만들어 주세요. 색이나 글꼴이 아니라 영역의 순서와 요소 유형이 달라야 합니다.
2. 배치안마다 화면 목록의 화면별로 표를 만들어 주세요. 열: 영역 순서 · 보여 줄 대상 객체와 속성 · 요소 유형(카드, 목록, 표, 차트, 탭, 펼치기, 버튼, 칩, 단계 선택, 입력 칸, 알림 띠) · 이 화면에서 꼭 되어야 하는 동작
3. 배치안마다 service-structure.md의 "가장 중요한 과업"을 몇 번 눌러 끝낼 수 있는지, 잘 맞는 상황과 약한 점을 한 줄씩 적어 주세요.
4. 화면 목록, 흐름 순서, 메뉴 순서, "화면에 쓸 말", "하지 말 것"은 바꾸지 마세요.
5. 마지막에 어느 안을 권하는지와 이유, 그리고 제가 정해야 할 것을 목록으로 남겨 주세요.
```

**결과.** 배치안 2~3개가 화면별 표로 나오고, 맨 끝에 권장안과 "정해야 할 것" 목록이 붙습니다.

**확인.**

- [ ] 배치안끼리 영역의 순서나 요소 유형이 다르다 (색 이야기만 다르면 다시 지시)
- [ ] 화면 이름이 `screen-flow.md` 화면 목록과 같고, 새 화면이 없다
- [ ] 화면마다 "꼭 되어야 하는 동작"이 적혀 있다
- [ ] 수치를 적었다면 `data` 폴더 CSV의 값이다

**계획 끝에 "이대로 진행할까요?" 같은 승인 버튼이 뜨면 승인하지 않습니다.** 승인하면 바로 파일을 만들기 시작합니다. 거절하거나 그대로 두고, 모드를 **Manual**로 바꾼 뒤 2단계로 갑니다.

**다를 때 다시 지시하는 문장.**

- 배치안이 색·분위기만 다르다 → "디자인 이야기는 빼고, 영역 순서와 요소 유형이 서로 다른 배치안으로 다시 세워 주세요."
- 화면이 늘었다 → "screen-flow.md 화면 목록에 없는 {화면 이름}은 빼 주세요. 그 내용이 필요하면 목록에 있는 화면 안에 넣어 주세요."
- 한 안만 나왔다 → "방향이 다른 안을 하나 더 세워 주세요. 예를 들어 {입력이 먼저 오는 안 / 비교해 보기가 먼저 오는 안}처럼요."

## 2단계 · grip-it으로 배치 결정하기

**지시.** 모드가 Manual인지 확인하고, 같은 대화에서 이어서 보냅니다. `/grip-it`은 입력창 **맨 앞에** 씁니다.

```text
/grip-it
참조 범위: 방금 세운 화면 배치안 계획, @context/service-structure.md, @context/screen-flow.md
관심 방향: 디자인을 입히기 전에, 화면마다 올라갈 요소 유형과 배치를 확정한다.
완료 조건: 기준 배치안과 그 안에서 남은 결정이 모두 정해지면 끝. 질문은 {6}개까지.
반영할 곳: 확정한 배치는 context/screen-layout.md 에, 결정 기록부는 context/grip-register.md 에 저장한다. 다른 파일은 고치지 않는다.
screen-layout.md 에는 아래 세 부분을 둔다.
- 화면별 배치: 화면마다 영역 순서 · 보여 줄 대상 객체와 속성 · 요소 유형
- 지킬 것: 흐름의 순서와 과업에 꼭 필요한 동작. 테마를 입혀도 바꾸지 않는다
- 바꿔도 되는 것: 테마가 바꿀 수 있는 배치와 요소 유형
```

**결과 ① 정할 것 목록.** grip-it은 바로 묻지 않고, 정할 것 전체를 먼저 보여 줍니다. 항목마다 **CORE**(되돌리기 어렵고 다른 결정을 묶는 것: 화면 순서, 꼭 필요한 동작의 자리)와 **MINOR**(쉽게 바꿀 수 있는 것: 요소 모양) 표시와 먼저 정할 순서가 붙습니다.

**결과 ② 하나씩 묻기.** 한 번에 한 가지씩 선택지 창이 뜹니다. 첫 번째가 권장안이고, 이유가 한 줄 붙어 있습니다. 마지막 선택지는 직접 쓰는 칸입니다.

- 권장안이 맞으면 그대로 고릅니다.
- 마음에 드는 안이 없으면 직접 쓰는 칸에 내 말로 적습니다. 예) "안 2의 순서로 하되, 지난 기록 비교는 안 3처럼 같은 화면에"
- 낯선 말이 있으면 창 아래 `[용어]` 풀이를 읽고 고릅니다. 뜻을 모르는 채로 고르지 않습니다.
- 고를 때마다 Claude Code가 `screen-layout.md`와 `grip-register.md`에 적었다고 알려 줍니다(파일을 만들 때 허락을 묻습니다. 작업 폴더 안이면 허락합니다).

**이렇게 나오면 정상입니다.** `context` 폴더에 `screen-layout.md`와 `grip-register.md`가 생기고, `screen-layout.md`에 화면별 배치 · 지킬 것 · 바꿔도 되는 것 세 부분이 있습니다. 대체로 CORE로 정한 것은 "지킬 것"에, MINOR로 정한 것은 "바꿔도 되는 것"에 들어갑니다.

**확인.** `screen-layout.md`를 열어 봅니다.

- [ ] "지킬 것"에 서비스 구조 설명서 8번 「하지 말 것」과 부딪히는 줄이 없다
- [ ] "지킬 것"이 순서와 동작만 말하고, "카드로 보여 준다"처럼 모양까지 묶지 않는다
- [ ] "바꿔도 되는 것"이 비어 있지 않다 (비어 있으면 테마끼리 차이가 나지 않습니다)

**다를 때.**

- 질문이 너무 많다 → "남은 질문은 권장안대로 정하고 마쳐 주세요. 무엇을 권장안으로 정했는지 목록으로 알려 주세요."
- 중간에 멈췄다 → 새 대화에서 "/grip-it context/grip-register.md 를 읽고 남은 결정부터 이어 주세요."
- "지킬 것"에 모양이 들어갔다 → "screen-layout.md 의 지킬 것에서 '{카드로 보여 준다}'를 바꿔도 되는 것으로 옮기고, 지킬 것에는 '{무엇이 무엇보다 먼저 보인다}'처럼 순서만 남겨 주세요."

### 예시로 보기

아래 예시 설명서로 1~2단계를 하면 이런 모양이 됩니다. 이 설명서는 이 가이드를 위해 만든 예시이고, 교재의 네 프로필 중 누구의 것도 아닙니다. 1~2단계 결과는 줄여서 옮겼고, 내 결과는 내 설명서에 따라 달라집니다.

**예시 서비스 구조 설명서 (배치에 쓰이는 부분만)**

```markdown
## 1. 서비스와 사용자
- 서비스: 운동 관리가 중심인 앱이다. PT를 받는 날과 혼자 운동하는 날 사이를 잇고, 운동 전후 몸 상태와 불편한 곳을 보고 오늘 강도를 정하도록 돕는다.
- 사용자: 3년 넘게 주 3~4회 운동한 중급자. 평일 저녁에 혼자 웨이트를 하고, 주 1회 PT를 받는다. 기록은 가끔 남기고, 안 남기는 날도 있다.
- 가장 중요한 과업: 무게를 올린 날 어깨 운동이 갑자기 힘들게 느껴질 때, 부상 신호인지 그냥 무거운 건지 가려서 다음 운동을 조정하고 싶다.

## 2. 대상 객체와 핵심 속성 (일부)
- 운동 세션: 날짜, 상태(계획 · 완료 · 미룸 · 건너뜀), 유형(혼자 · PT) (선택: 운동 부위)
- 컨디션 체크: 날짜, 시점(운동 전 · 운동 후), 컨디션 점수(1~5)
- 세트: 순서 (선택: 반복 수, 중량(kg), RPE)
- 신체 신호: 일시, 부위, 종류(통증 · 뻐근함 · 이상 감각), 불편감 점수(0~10), 통증 점수(0~10)
- 코칭 메모: 내용, 종류(자세 교정 · 무게 · 가동성 · 기타)

## 5. 화면에 쓸 말 (일부)
- 운동 세션 = "운동", 컨디션 체크 = "몸 상태" (운동 전 "지금 몸 상태"), 운동 종목 = "동작"
- 운동 세션.운동 부위 = "오늘 할 부위", 세트.중량 = "중량", 세트.반복 수 = "○회"
- 컨디션 체크.컨디션 점수 = "몸 상태 5단계" (무거움 ~ 가벼움, 숫자 대신 낱말)
- 세트.RPE = "힘든 정도 (RPE)", 신체 신호 = "불편한 곳" (버튼 "불편한 곳 남기기")
- 신체 신호.불편감 점수 = "불편한 정도", 신체 신호.통증 점수 = "아픈 정도", 코칭 메모 = "PT 노트"

## 6. 메뉴와 위치 표시
- 메뉴는 4개, 이 순서로 둔다: 1) 운동 2) 동작별 기록 3) 불편한 곳 4) 연결한 기기 · 앱
- 화면 이름: 운동 일정 · 운동 기록 · 운동 상세 · 동작별 기록 · 동작 상세 · 루틴 · 불편한 곳 · 불편한 곳 상세 · 연결한 기기 · 앱 · 내 정보

## 8. 하지 말 것 (일부)
- 불편한 곳을 세트에 반드시 묶지 않는다. 운동 없이도 남길 수 있어야 한다.
- 불편한 정도 · 아픈 정도 · 힘든 정도(RPE)를 하나로 합치거나, 구분 없이 같은 모양으로 나란히 두지 않는다.
- 불편한 곳이 있다고 무조건 운동을 멈추라고 하지 않는다. "계속 · 중량 낮추기 · 멈추기" 중에서 사용자가 고르게 한다.
- 진단 · 처방처럼 말하지 않는다.
```

**1단계에서 나오는 배치안 (운동 상세 화면만)**

| 배치안 | 영역 순서 | 잘 맞는 상황 | 약한 점 |
|---|---|---|---|
| 안 1 · 기록 먼저 | 오늘 할 부위와 동작 목록 → 세트 입력 줄(중량 · ○회 · 힘든 정도) → 운동 후 몸 상태 | 기록을 빨리 남기고 싶을 때 | 불편한 곳을 남길 자리가 세트 뒤로 밀림 |
| 안 2 · 몸 상태 먼저 | 지금 몸 상태(단계 선택) → 불편한 곳 확인, 있으면 "계속 · 중량 낮추기 · 멈추기" 고르기 → 세트 입력 | 부상 신호인지 가리는 가장 중요한 과업 | 운동 전에 한 단계를 더 누름 |
| 안 3 · 동작별 비교 | 동작마다 지난 세트 표 + 중량 변화 차트 + PT 노트 → 그 아래 오늘 세트 입력 | 무게를 올린 날 지난 기록과 견줄 때 | 화면이 길어져 모바일에서 많이 내려야 함 |

**2단계에서 grip-it이 펼치는 정할 것**

| 정할 것 | 종류 |
|---|---|
| 기준 배치안 (안 2 + 안 3의 지난 세트 비교 섞기 등) | CORE |
| 세트를 입력하는 중에 "불편한 곳 남기기"를 어디서 누를 수 있게 할까 | CORE |
| 불편한 정도 · 아픈 정도 · 힘든 정도(RPE)를 한 화면에서 어떻게 나눠 둘까 | CORE |
| 지난 세트를 표로 볼까, 줄 목록으로 볼까 | MINOR |
| 몸 상태 5단계를 버튼 줄로 볼까, 단계 선택 막대로 볼까 | MINOR |

**결정한 뒤 `screen-layout.md`에 들어가는 줄 (일부)**

```markdown
## 지킬 것
- 운동 상세: 지금 몸 상태 → 불편한 곳 확인 → 세트 입력 순서로 보인다
- 불편한 곳이 있으면 "계속 · 중량 낮추기 · 멈추기" 중에서 사용자가 고른다
- 불편한 정도 · 아픈 정도 · 힘든 정도(RPE)는 따로 보이고 따로 입력된다
- 어느 세트에서든 "불편한 곳 남기기"를 누를 수 있다

## 바꿔도 되는 것
- 지난 세트: 표 · 줄 목록 · 카드
- 몸 상태 5단계: 버튼 줄 · 단계 선택 막대 · 낱말 칩
- 중량 변화: 선 차트 · 막대 · 숫자 비교만
- 메뉴 모양: 위쪽 탭 · 왼쪽 메뉴 · 모바일 아래쪽 탭 (메뉴 순서는 그대로)
```

"지킬 것"의 줄들은 예시 설명서 8번 「하지 말 것」(멈추라고만 하지 않기, 세 점수를 하나로 합치지 않기, 불편한 곳을 세트에 꼭 묶지 않기)이 화면에서 지켜지게 하는 줄입니다. 내 설명서에서도 8번의 줄마다 "화면에서는 무엇이 되어야 하나"를 물어 보면 지킬 것이 나옵니다.

## 3단계 · 디자인 없는 배치 뼈대 만들고 확인하기

테마를 입히기 전에, 정한 배치만으로 눌러지는 뼈대를 하나 만듭니다. 흐름 · 문구 · 수치 문제를 여기서 한 번 고쳐 두면 테마마다 같은 문제를 고치지 않아도 됩니다.

**지시.**

```text
@context/service-structure.md @context/screen-flow.md @context/screen-layout.md 를 먼저 모두 읽어 주세요.
디자인을 입히기 전의 배치 뼈대 프로토타입을 만듭니다.

1. screen-layout.md 의 화면별 배치대로 화면을 만들고, screen-flow.md 의 기본 흐름과 갈림길대로 버튼을 이어 주세요.
2. 색은 흰색 · 회색 · 검정만, 글꼴은 기본 글꼴 하나만 씁니다. 장식과 그림자는 넣지 않습니다.
3. 화면 제목 · 메뉴 · 버튼 문구는 service-structure.md 의 "화면에 쓸 말"만 씁니다.
4. 수치는 data 폴더의 CSV 값만 씁니다. 없는 수치를 지어내지 마세요.
5. AI 판단 문장은 예시로 넣고, 어떤 기록을 근거로 했는지 함께 적어 주세요.
6. 결과는 prototype-layout.html 한 파일로, 데스크톱과 모바일 폭 모두에서 보이게 해 주세요. 외부 라이브러리 없이 더블클릭하면 열리게 해 주세요.

시작하기 전에 이해한 내용을 다섯 줄로 요약하고, 모호한 점이 있으면 먼저 질문해 주세요.
```

**확인과 수정.** 교재 3.6의 확인 목록 네 가지(흐름대로 끝까지 눌러지는가 · 이름이 용어 대조표와 같은가 · 숫자가 CSV 값과 같은가 · 모바일 폭에서 쓸 만한가)를 「[Claude Code 프로토타이핑 따라 하기](claude-code-prototyping-guide.md)」 2단계의 방법으로 점검하고, 같은 가이드 3단계처럼 한 번에 한 가지씩 고칩니다. 하나를 더 봅니다.

- [ ] `screen-layout.md`의 "지킬 것"을 한 줄씩 직접 눌러 보면 모두 된다

**이렇게 나오면 정상입니다.** 회색조의 밋밋한 화면이 흐름대로 끝까지 눌러집니다. 밋밋한 것이 정상입니다. 디자인은 4단계에서 입힙니다.

배치를 고치다가 "지킬 것"이 바뀌었다면 `screen-layout.md`도 같이 고쳐 달라고 합니다. 예) "방금 바꾼 순서를 screen-layout.md 의 지킬 것에도 반영해 주세요. 다른 줄은 바꾸지 마세요."

## 4단계 · 테마마다 디자인 입히기

교재 70쪽 1단계(첫 프로토타입 지시문)와 3단계(테마별 프로토타입 추가 생성 지시문) 대신 이 지시문을 씁니다. 교재 3단계는 "화면 구성은 똑같이 두고 디자인만 바꾸라"고 하지만, 여기서는 **지킬 것만 지키면 배치와 요소 유형을 바꿔도 된다**고 지시합니다. 첫 테마는 시안 비교표의 한 줄 결론에서 고른 테마로 합니다.

**지시.**

```text
@context/service-structure.md @context/screen-flow.md @context/screen-layout.md @design/DESIGN-{테마이름}.md 를 먼저 모두 읽고,
@prototype-layout.html 에 디자인을 입힌 prototype-first-{테마이름}.html 을 새로 만들어 주세요.
prototype-layout.html 은 고치지 마세요.

[지킬 것 — 바꾸지 않습니다]
- screen-flow.md 의 화면 목록과 흐름 순서, 버튼이 이어지는 곳
- screen-layout.md 의 "지킬 것"에 적힌 순서와 꼭 되어야 하는 동작
- 화면 제목 · 메뉴 · 버튼 문구("화면에 쓸 말")와 data 폴더의 수치
- 색만으로 의미를 구분하지 않기

[바꿔도 됩니다 — DESIGN-{테마이름}.md 에 더 잘 맞는다면]
- 영역의 배치: 위아래 · 좌우, 한 화면에 모으기 · 나누기
- 요소 유형: screen-layout.md 의 "바꿔도 되는 것"과 같은 전환 (예: 표 ↔ 목록 ↔ 카드, 버튼 줄 ↔ 단계 선택 ↔ 칩, 선 차트 ↔ 막대 ↔ 숫자 비교)
- 정보를 얼마나 촘촘하게 둘지, 무엇을 크게 강조할지, 색 · 글꼴 · 간격 · 모양
테마마다 다르게 보이는 것이 목표입니다. 지킬 것만 지키면 과감하게 바꿔도 됩니다.

만들기 전에 바꿀 배치와 요소 유형을 "화면 · 영역 | 지금 → 바꿀 모습 | DESIGN.md 의 어느 규칙 때문인지" 표로 먼저 보여 주세요. 제가 확인한 뒤 만들어 주세요.
다 만든 뒤에는 지킬 것을 한 줄씩 확인한 결과를 목록으로 알려 주세요.
```

**결과 ① 바꿀 것 표.** 만들기 전에 "어디를 무엇에서 무엇으로, 왜" 바꿀지 표가 나옵니다. 지킬 것을 건드리는 줄이 있으면 그 줄만 빼 달라고 하고, 나머지가 괜찮으면 "좋습니다. 이대로 만들어 주세요."라고 보냅니다.

**결과 ② 테마 파일.** `prototype-first-{테마이름}.html`이 생기고, 지킬 것 확인 결과가 나옵니다.

**둘째 · 셋째 테마.** 같은 지시문에서 테마 이름만 바꾸고, 셋째 줄 아래에 한 줄을 더해 보냅니다.

```text
이미 만든 prototype-first-{첫 테마이름}.html 도 고치지 마세요. 이 테마는 그 파일과 다르게 보여도 됩니다.
```

테마마다 `prototype-layout.html`에서 출발하므로, 앞 테마의 배치를 따라가지 않습니다.

**다를 때 다시 지시하는 문장.**

- 색만 바뀌고 배치가 똑같다 → "DESIGN-{테마이름}.md 의 {분위기 · 부품} 규칙에 맞게 바꿔도 되는 것을 더 바꿔 주세요. 바꿀 것 표를 다시 보여 주세요."
- 꼭 되어야 하는 동작이 사라졌다 → "{화면 이름}에서 '{지킬 것 한 줄}'이 안 됩니다. 요소 유형은 지금처럼 두고 이 동작만 다시 되게 해 주세요."
- 화면 이름이나 문구가 바뀌었다 → "{바뀐 문구}를 service-structure.md 의 '화면에 쓸 말'인 '{쓸 말}'로 되돌려 주세요. 배치는 그대로 두세요."
- 지킬 것까지 바뀌었다 → 「[Claude Code 프로토타이핑 따라 하기](claude-code-prototyping-guide.md)」 3단계의 "고쳤더니 다른 곳도 바뀌었다" 문장으로 그 부분만 되돌립니다.

## 5단계 · 나란히 열어 비교하기

`prototype-layout.html`과 테마 파일들을 브라우저 탭에 나란히 열고, 같은 화면을 오가며 봅니다.

| 볼 것 | 보는 방법 |
|---|---|
| 지킬 것이 모두 되는가 | `screen-layout.md`의 "지킬 것"을 테마 파일마다 한 줄씩 눌러 봅니다. 하나라도 안 되면 4단계의 다시 지시하는 문장으로 고칩니다 |
| 무엇이 바뀌었나 | 같은 화면에서 배치 뼈대와 다른 곳을 찾습니다. 위치가 바뀐 영역, 모양이 바뀐 요소(표 → 카드 등), 커지거나 작아진 것 |
| 바뀐 것이 과업에 도움이 되나 | 가장 중요한 과업을 테마마다 처음부터 끝까지 해 보고, 더 빨리 끝나거나 더 잘 읽힌 곳을 적습니다 |
| 화면의 느낌 | 첫눈에 어떤 서비스처럼 보이는지 한 낱말로 적습니다. 예) 차분한 기록장, 다정한 코치 |

### 짝과 5분 · 테마 느낌 맞혀 보기

내가 적은 "화면의 느낌"이 다른 사람 눈에도 그렇게 보이는지 짝에게 확인합니다. 둘이 합쳐 5분입니다.

1. 테마 파일 두 개를 같은 화면으로 열어 짝에게 차례로 보여 줍니다. 테마 이름과 DESIGN.md는 미리 말하지 않습니다.
2. 짝은 테마마다 "어떤 서비스처럼 보이는지" 한 낱말로 말합니다.
3. 짝이 말한 낱말을 내가 적은 낱말 옆에 적습니다. 둘이 다르면 "어디를 보고 그렇게 느꼈어요?"라고 한 가지만 묻고, 짝이 가리킨 화면 영역을 함께 적습니다.
4. 역할을 바꿔 짝의 테마도 봅니다.

짝은 상대의 작업을 대신하지 않고 본 느낌만 말해 줍니다. 짝이 말한 낱말과 가리킨 영역은 6단계 버전 기록의 "바뀐 점·관찰 메모"에 함께 옮겨 둡니다.

확인 목록 네 가지에서 문제가 나오면 「[Claude Code 프로토타이핑 따라 하기](claude-code-prototyping-guide.md)」 3단계처럼 한 번에 한 가지씩, 테마마다 두세 번까지만 고칩니다.

그다음 상태 화면(교재 71쪽 4단계)과 신뢰 요소(교재 3.7절)는 교재와 지시문 킷 그대로 테마 파일마다 넣습니다. 「[Claude Code 프로토타이핑 따라 하기](claude-code-prototyping-guide.md)」 5~7단계를 따라갑니다. 넣은 뒤에도 "지킬 것"이 되는지 한 번 더 눌러 봅니다.

## 6단계 · 버전 기록에 남기기

워크시트 문서의 「테마별로 만든 첫 프로토타입과 버전 기록」에 테마마다 한 줄씩 씁니다. 칸은 교재 71쪽 표 그대로이고, 이 흐름에서는 세 칸을 이렇게 채웁니다.

| 칸 | 이 흐름에서 쓰는 것 |
|---|---|
| 만든 때 (지시문 이름) | Day 3 · 3.6 (배치 뼈대 → 테마 입히기 → 수정 {n}회 → 상태 화면·신뢰 요소 추가 지시문) |
| 바뀐 점·관찰 메모 | 5단계에서 찾은 "배치 뼈대에서 바뀐 곳"과 과업에 도움이 된 곳. 예) 지난 세트가 표 → 카드, 모바일에서 더 잘 읽힘 |
| 근거 | `context/screen-layout.md`의 지킬 것 · 화면 흐름 순서표의 기본 흐름 |

배치 뼈대 `prototype-layout.html`은 버전 기록에 행을 만들지 않아도 됩니다. 테마 파일의 출발점으로 작업 폴더에 남겨 두고, 배포 폴더 `deploy/`에는 넣지 않습니다.

Day 4 통합(4.2절)에서 영역을 골라 올 때, 테마마다 배치와 요소 유형이 달라도 화면 이름과 지킬 것이 같으므로 화면 · 영역 단위로 고를 수 있습니다. 통합 지시문의 "지킬 것"에 `context/screen-layout.md`의 지킬 것을 함께 가리키면 통합한 뒤에도 꼭 필요한 동작이 남습니다.

## 자주 하는 실수와 고친 예

| 실수 | 고친 예 |
|---|---|
| 배치안이 색과 분위기만 다르다. 예) 도서관 앱 배치안 1은 파란색, 배치안 2는 초록색이고 영역 순서는 같다 | "디자인 이야기는 빼고, 대출 중인 책이 먼저 오는 안과 검색이 먼저 오는 안처럼 영역 순서가 다른 안으로" 다시 받는다 |
| "지킬 것"에 모양까지 적어 테마끼리 차이가 없다. 예) 가계부 앱의 지킬 것에 "이번 달 지출을 카드로 보여 준다" | 지킬 것은 "이번 달 지출이 첫 화면 맨 위에 보인다"(순서)로, "카드"는 바꿔도 되는 것으로 옮긴다 |
| 요소 유형을 바꾸다가 꼭 필요한 동작이 숨었다. 예) 배달앱의 주문 내역을 펼치기로 바꿨더니 "주문 취소" 버튼이 펼쳐야만 보인다 | 지킬 것에 "주문 상세에서 주문 취소를 바로 누를 수 있다"를 넣고, 그 동작만 다시 되게 해 달라고 한다 |
| 둘째 테마를 첫 테마 파일에서 만들어 배치가 비슷하다 | 둘째 테마도 `prototype-layout.html`에서 출발하게 4단계 지시문을 다시 보낸다 |
| Plan 모드의 승인 버튼을 눌러 배치안 계획대로 바로 파일이 만들어졌다 | 만들어진 파일은 지우지 말고 이름 끝에 `-before-grip`을 붙여 두고, 모드를 Manual로 바꾼 뒤 2단계부터 한다 |

## 막혔을 때

- **`/` 목록에 grip-it이 없다.** 새 대화를 열어 다시 봅니다. `.claude/skills/grip-it/SKILL.md` 경로와 대문자 `SKILL.md`를 확인합니다. 그래도 없으면 1단계 결과 아래에 "배치안 사이에서 제가 정해야 할 것을 하나씩, 권장안과 이유를 붙여 선택지로 물어봐 주세요. 정한 것은 context/screen-layout.md 에 지킬 것 · 바꿔도 되는 것으로 나눠 적어 주세요."라고 보냅니다.
- **grip-it이 결정을 다른 폴더에 저장하려 한다.** 거절하고 "결정 기록부는 context/grip-register.md, 확정한 배치는 context/screen-layout.md 에만 저장해 주세요."라고 다시 말합니다.
- **시간이 모자란다.** 테마는 두 개만 만들고, 1단계 배치안은 2개, 2단계 질문은 3~4개로 줄입니다. 3단계 배치 뼈대를 건너뛰어야 한다면 4단계 지시문의 `@prototype-layout.html 에 디자인을 입힌`을 `@context/screen-layout.md 의 배치에 디자인을 입힌`으로 바꿔 보냅니다. 「[Claude Code 프로토타이핑 따라 하기](claude-code-prototyping-guide.md)」의 「작업 진도가 뒤처질 때 대처 방안」도 같이 봅니다.
- **사용량 한도가 다 되었다.** 다른 AI 코딩 도구에서 grip-it은 Codex는 저장소의 `.agents/skills/grip-it/SKILL.md`, Cursor는 `.cursor/skills/grip-it/SKILL.md`를 작업 폴더의 같은 경로에 저장해 씁니다. 도구 차이는 「[다른 AI 코딩 도구로 할 때 (OpenAI Codex · Cursor)](../help/other-coding-tools.md)」를 봅니다.
